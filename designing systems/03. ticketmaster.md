## 1. Requirements

Functional: features

User should be able to...

- purchase ticket for an event
  - retrive the tickets
  - cancel the ticket
- view event
- search events

Non-functional: qualities

- go to the `ilities` in the context of this given application. Ask yourself (in this order)

```
1. CAP theorem: Consistency or Availability?
2. Read-write ratio: Will users write or read more?
  - in this application 100/1000:1
3. Query access pattern: How does the application read/write data?
  - what's the frequency/consistenty/regularity of requests?
  - in this app, frequent most of the time. From time to time, super popular ones (world cup, big concert, etc)
  - in this app, handle increased load volume
```

- consistency > availability
  - User shouldn't be able to purchase already bought ticket (no double booking)
  - it's not okay someone see outdated information
- low latency when buying the tickets
- low latency search
- strong consistency for booking tickets
- high availability for search and viewing events

**different parts of the system can have different CAP priorities!**

You can note down other non-functional requirements as out of scope for this conversation, but you can talk about reprioritizing if needed

## 3. API

```ts
// view event
GET event/{id} -> Event & Venue & Performer & Ticket[]

// search event
GET search/?term={term}&location={location}&category={category}... -> Event[]

// buy a ticket
// buying a ticket is usually a 2-step process (reserve [with time limit] + buy)
POST tickets/reserve
HEADER: JWT | sessionToken // user information should only be here!
{
  ticketId,
  // ideally, you don't accept an userId or a body -> security concern
}

POST tickets/confirm
HEADER: JWT
{
  ticketId,
  paymentDetails, // stripe
}

// retrive tickets
GET tickets/{userId}?event={eventId}
```

## 4. High-level Design

- How do we make the ticket expire?

1. most basic: add a field `reserveTimestamp` on the `Ticket`

- then use this on the query if ticket is available or if `reserveTimeStamp` > 10min

2. medium level: have a cron job

- instead of using the `reserveTimeStamp` on a query, we hava a cron job that will be monitoring the db
- if the reserveTimeStamp > 10min, then make it available again

3. advanced: instead of a cron job with relies on a field, we can have a ticket lock (redis) | distributed lock

- {ticket: true} TTL 10min
- then when the user clicks on reserve, we don't put that ticket to the db, we set it on the cache
- when someone else GET availableTickets, we grab all the available tickets, but filter out the ones that are reserved on the cache
- what if this one goes down?
  - users that have done a reservation in the last 10 min would have their reservation lost

## 5. Deep dive

- 1-3 places where you can go deep
- Reference the non-functional requirements

### How can we optimize the search? (low-latency search)

1. introduce a low-latency db search, e.g. elasticsearch

- in questions of search, usually elasticsearch is a great option
- how do we get data into elasticsearch?
  - elasticsearch shouldn't be used as the main db, only a5s a companion one to improve search queries
  - changes in the main db should be propagated to elastic search
  - there are two ways to do it:
    1. through application code events
    - if an event is added, send it to postgres and to elastic search
      - what if one the writes fail? it shouldn't be propagated to the other
      - it increases the complexity and reduces fault tolerance
    2. change data capture (CDC)
    - changes to a primary datastore can be propagated (data is put into a stream and events are created to be consumed)
    - queues could also work

### What about popular queries?

1. aws opensearch has **node query caching**

- it stores the top 10k queries in a least recently used cache

2. we could add a cache before elasticsearch
3. CDNs can cache search terms

- great for popular events

### Scalability to handling surges from popular events

- Let's say the user loads the event and sees the seat map and other users are doing the same
- On the current structure, we'd hit the book service, reserve the ticket for that user
- This data can go stale after 1, 2, 5 minutes and users would see/don't see seat maps that would/wouldn't be available
- How can we deal with this very popular events?
  - real-time seatmap
    1. long polling
    2. persistent connection:
    - sse: server sent events
      - unidirection: only the server is sending data
    - web-sockets
      - bidirectional: client and server are sending data
  - virtual waiting queue: handling massive ticket demand
    - only enabled for popular events
      - like a field, etc
      - if an event is programmed to have, let's say more than 1M, we enable this
      - then, people will have their position on the queue so they can reserve
