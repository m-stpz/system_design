# Ticketmaster

- Online platform that allows users to purchase tickets for concerts, sports events, theather, and other live entertainment
  - Has ~100M DAU

## The Approach

1. Requirements: functional and non-functional
2. Core entities
3. API
4. High-level: satisfies functional
5. Deep dive: satisfies non-functional

## Requirement

Functional: features

User should be able to...

- purchase ticket for an event
  - retrive the tickets
  - cancel the ticket
- view event
- search events

Non-functional: qualities

- go to the `ilities` in the context of this given application
- **first question to ask yourself is the CAP theorem. Should my system prioritize consitency or availabilty?**

- consistency > availability
  - User shouldn't be able to purchase already bought ticket (no double booking)
  - it's not okay someone see outdated information
- low latency when buying the tickets

## Core entities

Ticket

- userId
- timeOfPurchase
- eventId

Event

- name
- characteristics
- ticketsSold

## API

```ts
// buy a ticket
POST tickets/
{
  userId,
  eventId,
}

// retrive tickets
GET tickets/{userId}?event={eventId}

// view event
GET event/{id}

// search event
GET event/{id}?name={name}&characteristics={characteristics}
```
