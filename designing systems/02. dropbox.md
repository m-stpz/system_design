# Dropbox

- Cloud-based file storage service that allows users to store and share files
- Secure and reliable way to store and access files from anywhere, on any device

1. Requirements
2. Core entities
3. API
4. High-level design

## 1. Requirements

Functional requirements: what the system does

- Upload a file
- Download a file
- Share a file
- Automatically sync files across devices

Out of scope

- Roll own blob storage

Non-functional requirements: how the system behaves | what informs the deep-dives later on

- Consistency or availability? Availability > consistency
  - it's ok if we update the data and someone when accessing it, sees a "outdated" version for a while
  - functionality should continue working, no matter what. it's fine eventual consistency
- low latency upload and download
- support large files as 50gb
  - resumable uploads
- high data integrity (sync accuracy)

## 5. Deep dives | Satisfies the non functional requirements

### How do we support large files?

- request bodies usually have a limit of 10mb. How can we upload a file of 50gb?
- upload directly to S3
  - non-everyone should be able to upload to s3

1. upload first just the metadata
2. set status to "started" on `file metadata`
3. ask blob storage for a pre-signed url
4. return the pre-signed url for the client and the client uploads directly to s3 with pre-signed url

### How do we handle the upload of this large file?

- 50gb will take a while and errors can occur on the process. How do we handle this?
- Chunking
  - chunk on the client to 5mb chunks
  - we need to keep track of which chunks have been uploaded
    - on the file metadata, we have either an object or a foreign-key, if it's another table
    - as the documents are uploaded successfully, we update this value
    - once all the chunks are uploaded, we change the status to "success"
    - what if the upload process is interrupted?
      - we compare the client chunks with the chunks on the `file metadata`
      - then we know where we stopped
  - to identify the chunks, we can fingerprint each chunk: hash(bytes)

### How do we inform the success of a chunk upload to blob storage?

- Ideally, we shouldn't trust the client

❌ bad: trust the client

1. client gets pre-signed url
2. client uploads chunks to blob storage
3. blob storage returns success to the client
4. client does a request to the system informing of "success"

this is dangerous and error prone

✅ good: here, a possible solution is "trust, but verify"

1. client gets pre-signed url
2. client uploads chunks to blob storage
3. blob storage returns success to the client
4. client does a request to the system informing of "success"
5. file service takes the information from the client and checks with blob storage, "is this correct?"

✅ good: triggers on blob storage

1. client gets pre-signed url
2. client uploads chunks to blob storage
3. successful uploads on blob storage triggers a notification to the file service

### How do we keep latency for upload/download as short as possible?

- Chunking is quite helpful here
  - specially parallel chunking
- CDN is this case might not be a good solution since users will be mainly downloading their own files. So, they are located close to the source
  - perhaps then we also have:
    1. traveling users
    2. a popular file that is accessed/shared by multiple people
    - however this is a minority. So, it doesn't seem to justify the usage of a CDN, which is rather expensive to maintain

- Compressing
  - text/docx compress well
  - PNG, JPEG are already well compressed, so it wouldn't be worth the effort to compress/decompress them
  - should I compress or not?
    - it depends on the file

### How do we keep strong file sync?

Sync should be:

- fast
  - how can we make it fast?
    1. periodical checks + adaptive frequency
    - this polling can be adjusted based on if the app is open, if there were many changes in a short time, etc
    - in any case, if the user really wants to see a file, there can be a "refresh" button
      1.2. web-sockets for this app aren't a good call since they'd keep the connection alive whenever basically you're using your pc
    2. delta sync: only get the chunks that have changed
    - if a new file was added, then it must be downloaded
    - however, if the file was only changed, we get the bytes that changed
- consistent
  - how can we make it consistent?
    - 1. pull the db directly
      - add a `folderId` to the metadata
      - for `folderId`, get me any files for which the chunks have changed/been added since the last sync
    - 2. event bus
      - something like kafka
      - any change is added to this bus
      - a linear list of the events (like a log)
      - we navigate to the cursor (the last event we've read), and continue from there (like a linked list)

### How do we reconciliate?

- Local and cloud might fall of of sync (due to several reasons)
  - Periodically do reconciliation
